## 1. 本轮建设目标

本轮工作的核心目标是把原来依赖前端静态数据和 SVG 底图绑定的快速上线方案，改造成可长期维护的后台管理系统。后台需要能管理底图版本、POI 信息、标记点、路线图层、校车时刻、发布快照、日志、备份和管理员账号，并逐步把前端展示内容从代码内硬编码迁移到后端数据。

本轮重点解决了几类技术债：

- 底图更新后，POI 绑定和对象 Diff 需要有后台可视化处理，而不是手工改前端数据文件。
- POI 内容、图片、描述、属性和导航信息需要由后台管理，前端只负责按样式渲染。
- Marker 不应该和 SVG 建筑对象混在一起，需要独立的数据模型和管理页面。
- 楼内设施不应被迫手动点坐标，应能作为建筑附属标记点批量维护。
- 管理后台需要完整发布链路、日志、备份、导入导出和审计基础。

### 2.7 标记点逻辑重构

当前标记点底层仍使用三个 `display_mode`：

- `standalone`：独立点位，需要自己的地图坐标。
- `attached`：附属点位，显示在所属建筑中，不单独创建 POI 详情。
- `hybrid`：附属点位，但单独展示详情；坐标继承所属建筑，同时绑定或新建自己的 POI。

但后台不直接向管理员暴露 `attached` / `hybrid` 这类工程词，而是展示为两层选择：

- 点位类型：
  - 独立点位
  - 附属点位
- 附属点位的信息展示：
  - 显示在所属建筑中
  - 单独展示详情

对应关系：

| 后台选择 | 底层值 | 坐标来源 | 是否需要 POI 详情 |
| --- | --- | --- | --- |
| 独立点位 | `standalone` | 手动选点或填写坐标 | 可以绑定或新建 POI |
| 附属点位 + 显示在所属建筑中 | `attached` | 所属建筑坐标 | 不需要独立 POI |
| 附属点位 + 单独展示详情 | `hybrid` | 所属建筑坐标 | 必须绑定或新建 POI |

坐标继承逻辑：

1. 如果所属建筑本身绑定了 Marker，优先继承该 Marker 坐标。
2. 如果所属建筑绑定了 SVG 对象，则在后台前端从当前校区 SVG 中计算对象中心点。
3. 如果无法从所属建筑得到坐标，则保存时提示该建筑不可定位。

## 4. 当前核心数据逻辑

### 4.1 POI

POI 是信息主体，负责承载前端卡片内容。

主要字段：

- 名称
- 校区
- 分类
- 详情 JSON
- 导航 JSON
- 状态
- 绑定关系
- 属性 / 状态

POI 可以绑定：

- SVG 底图对象
- Marker
- 后续可扩展 Polygon / indoor space

### 4.2 POI 分类

POI 分类用于表达该 POI 是什么类型，例如：

- 建筑
- 食堂
- 图书馆
- 服务设施
- 校车点
- 运动场馆

分类是 POI 的主类型，不应承担设施筛选的全部职责。

### 4.3 POI 属性

POI 属性用于表达非定位类状态或补充信息，例如：

- 开放
- 可预约
- 有电梯
- 有卫生间

当前仍使用原 `poi_tags` 表，但后台展示和 API 命名已经改为“POI 属性”。后续如果需要彻底清理，可以再做物理表名迁移。

### 4.4 Marker

Marker 是具体地图标记点，可以代表：

- 公交站
- 地铁站
- 校车点
- 打印机
- 充电宝
- 饮水机
- 卫生间
- 浴室
- 商超
- 停车场入口

Marker 可以独立存在，也可以挂在建筑下。

### 4.5 Marker 类型

Marker 类型定义默认图标、颜色、显示策略、默认 POI 分类和默认点位模式。

当前后台展示为“标记类型”。可以继续叫“标记类型”，比直接翻译 Marker Type 更适合管理员。

### 4.6 POI 和 Marker 的关系

推荐规则：

- 建筑本身是 POI，绑定 SVG 对象。
- 楼内普通设施是附属 Marker，挂到建筑上，不单独创建 POI。
- 楼内需要单独展示详情的设施是附属 Marker，同时绑定或新建一个 POI。
- 校车点、公交站、地铁站等是独立 Marker，可以绑定自己的 POI。
- 前端渲染时，建筑卡片可以聚合展示附属设施；独立或单独展示详情的 Marker 可以打开自己的卡片。

## 8. 已知问题与风险

### 8.1 物理表名仍有历史语义

POI 属性当前仍使用旧表 `poi_tags` / `poi_tag_links`。后台和 API 已经改为 `poi-attributes`，但数据库物理表名尚未迁移。

短期可接受；正式上线前可考虑做一次重命名迁移，或者继续保留旧表名作为兼容层。

### 8.2 前端用户端还没有完全消费 Marker

后台已经能管理 Marker、Marker 类型和发布快照字段，但用户端地图对 Marker 的完整展示、筛选、点击、聚合和建筑附属设施展示还需要继续做。

### 8.3 室内空间只是预留

`indoor_spaces` 和 Marker 的 `parent_space_id`、`floor_id`、`indoor_position_json` 已预留，但楼层图上传、楼层切换、室内设施渲染还没有实现。

### 8.4 SVG 对象中心点计算依赖前端当前 SVG

附属点位坐标继承逻辑目前会在后台前端从当前校区 SVG 中计算对象中心点。更稳的方案是后续在 SVG 导入时写入 `bbox_json`，并让后端和前端都优先使用该字段。

### 8.5 权限模型仍然较粗

当前管理员只做账号新增和删除，没有细分角色和权限。现阶段符合需求，但以后如果多人维护校车、POI、地图版本，可能需要角色权限。

### 8.6 管理页仍需一轮真实数据验收

很多后台能力已经搭好，但还需要用真实 POI、真实标记点、真实校车路线跑一遍完整工作流，才能发现细节问题。

## 10. 迁移到社团 Cloudflare 账号的注意事项

本项目部署在 Cloudflare Workers 体系下，迁移时需要关注以下资源：

- Worker：`shumap`
- D1 数据库：`shumap`
- R2 Bucket：`shumap-assets`
- KV Namespace：`RELEASE_KV`
- Queue：`shumap-import`
- Worker secrets / vars
- 自定义域名和 DNS

迁移建议：

1. 在社团账号中创建同名或新命名资源。
2. 导出当前 D1 数据。
3. 导入到新 D1。
4. 迁移 R2 媒体资源。
5. 更新 `wrangler.jsonc` 中的资源 ID。
6. 重新设置 secrets。
7. 执行 `npm run build`。
8. 执行 `npx wrangler deploy`。
9. 检查 `/api/health`、`/admin/`、`/collect`。
10. 绑定正式域名。
