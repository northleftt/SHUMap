# 新旧客户端兼容与小程序审核发布方案（待实现）

## 2026-09-26 核对结果

- 当前全部客户端共用 `/api/public/releases/current`；请求未携带契约版本。
- 小程序云托管代理透传 URL 与 query，可使用查询参数分流，无须依赖包版本识别。
- 历史楼层改造前解析器：当前生产 manifest 通过；staging manifest 因 `floors[].imageUrl` 报错；删除此键后通过。此为历史代码验证，尚未证明其就是微信当前线上包。
- 最新客户端可解析当前生产与 staging 两种 manifest。
- manifest `schemaVersion` 目前严格等于 2，不能直接改为 3。
- 小程序 manifest 缓存当前只按 releaseId 区分，升级后同一 release 的不同投影存在复用风险。
- 公共地图资产仅允许当前 active release 成员读取，因此冻结旧 manifest 指针无法单独保证旧地图资产可读。
- 生产迁移目前至0034；新就餐及校历需要0035/0036。校历种子有效期需检查补全。

## 推荐协议

1. 新 Web、小程序请求 release 时显式携带 `?contract=2026-09`（示例常量名，实施时固定）。旧请求无参数默认 legacy，永久保持明确语义。
2. Worker 从同一当前内容发布生成两份契约响应。legacy 去除旧解析器不接受的键，例如 imageUrl；最新响应保留。维持旧必需键和类型，例如 indoorSpaceId=null。schemaVersion仍为2。
3. 仅面向客户端的接口按契约输出；内部发布校验、数据管理、资产权限继续使用原始canonical manifest，不通过legacy投影。
4. 新增就餐API是增量能力，旧端无调用；逐个核对校车、设施、地点详情等已有API的字段/枚举兼容，不整套API盲目分叉。
5. release/current 与版本指定读取必须采用同一策略。未知契约返回明确错误，避免静默返回不匹配结构。
6. URL区分契约自然隔离HTTP缓存，ETag按实际响应字节计算；content-length也需重算。小程序新缓存前缀包含契约与运行环境，防止旧包缓存污染新包。
7. release ID继续代表内容发布；contract代表解析能力；应用包版本代表产品版本。三者分别管理，不按日期/semver推测客户端能力。
8. 校区底图随发布切换时，需在兼容期保留确实属于已发布版本、且媒体仍获准公开读取的资产；撤销/删除资产仍应拒绝。仅允许显式保留发布集合，不能开放整个R2历史。

## 审核与上线

- 先在staging回放真实线上旧包/对应提交、新包、旧网页及新网页；覆盖冷缓存、旧缓存升级、发布回滚、图片和地图资产、云托管。
- 首次生产上线兼容后端与必要新增表/API，保障旧端使用原契约；新版提审包接入同一生产服务的新契约。新旧包同时存在是常态。
- 新审核包不因审核身份切换服务或数据；功能与以后发布的正式包保持一致。若希望网页界面等审核后一起切换，首轮兼容后端发布保留现网Web资产，需准备独立发布步骤；现有 deploy 脚本会同时重新构建Web，不能直接照跑。
- 提审冻结精确commit、AppID、应用版本、契约常量及prod配置。模拟器staging storage设置不等于上传包默认环境；必须从干净环境验证审核默认路径。
- 审核通过后发布新网页及小程序；继续保留legacy响应和必要资源。新增内容按客户端契约输出，旧端不支持位图时降级楼层列表。
- 应用版本可随请求上报供统计与排障；兼容移除依据真实旧端使用量及支持政策，不能假设发布日期过后所有设备已更新。
